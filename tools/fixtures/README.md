# Legacy link fixtures (baseline capture, task P0-A)

These files freeze how the calculators decoded share links **before** the
per-patch rework, so the reworked pages can be checked against them
(`tools/test-links.js`, the screenshot regression). They were generated by
`tools/capture-legacy.js` from the baseline commit
`9a0c627e3a814a2657fabceaceea34d782f1b2fc` ("Phones: main area shrinks to the
scaled stage; S1 Save button stays blue"), the last commit before the
rework. Do not edit them by hand.

| File | Content |
| --- | --- |
| `legacy-codecs.json` | The legacy mastery codecs of the 8 old mastery ids: array (= share-code) order, `ranks`, `hashRanks`, `hashNote`, grid `index`, `parentKey`, and the keystone tier lists |
| `legacy-links.json` | 586 seeded random valid builds over the 23 legacy ids (`{form, hash, expected, rewrite?}`) and the 23 baseline views |

## Running

```
node tools/capture-legacy.js fixtures --research <scratchpad>\patches   # regenerate (byte-identical on a re-run)
node tools/capture-legacy.js check    --research <scratchpad>\patches   # re-decode every record, exit 1 on a mismatch
node tools/capture-legacy.js verify-browser --out <dir>                 # the same records through the real pages (headless Edge/Chrome)
node tools/capture-legacy.js shots    --out <dir>                       # the 69 baseline screenshots
node tools/capture-legacy.js compare  <shotsA> <shotsB>                 # pixel diff with the measured noise allowance
```

* `--research` is the folder whose `raw/reforged/runesReforged-<ddragon>.json`
  holds the Data Dragon catalogs of the 10 Reforged ids (read only; the tool
  never touches the network for fixtures). `check` also verifies their
  sha256 against `about.reforgedCatalogs`.
* The code under test is read with `git show <rev>:<file>`; the default
  `<rev>` is the baseline commit. `--rev <commit>` or `--worktree` point it
  elsewhere (`check --worktree` on a reworked tree is expected to fail: the
  old data files are gone).
* `shots` and `verify-browser` export the commit with `git archive` into
  `<dir>/site-<short rev>` (or take `--root <site>`; `--worktree` copies the
  working tree first, so nothing is written into the repo). Node 22+ is
  needed for `shots` (built-in WebSocket).

## How the records are made

The page scripts that `index.html`, `runes.html` and `runes-reforged.html`
load (plus `air-sheet.js` for the mastery page name) run in a Node VM with a
chainable no-op `$` and a DOM in which no element exists. Builds are made
with the pages' own rules: classic points by legal `isValidState` clicks,
keystone points through `handleKeystonePickClick`, rune slots by category,
Reforged picks from the catalog rows and the era's shard table. The hash is
what the page itself writes (`updateLink` / `updateKeystoneLink` /
`buildReforgedHash`). Every record is then opened in a **fresh** VM page
(the ready handler runs, as when a link is opened in a new tab; Reforged
runs the catalog-loaded half of `activateReforgedDataSet`) and must decode
to `expected` and write back `rewrite` (or `hash` when there is no
`rewrite`). `verify-browser` repeats this in the real pages, DOM included
(586/586 at the baseline). Seeded PRNG per id, no timestamps.

Coverage per mastery id: the empty page, 40 random builds (about half at
30 points; 4 with a page name), extra builds until every mastery has been
at its max rank once, a name that the sidebar normalises, and:

* `s1-final`: `legacy-wide-field`: old links whose Preservation field holds
  2 or 3 (the 2-bit width of the old 3-rank Perseverance, `hashRanks: 3`).
  The value clamps to 1, `expected.notes` is the toast, `legacyValue` names
  the field. The clamped builds are valid and the old ones had at most 30
  points.
* `s4-final`, `s5-final`: `tilde` (Inspiration 2/2 needs `~` + a code in the
  current widths) and `tilde-fits-legacy` (a `~` code that also fits the
  legacy widths: re-exported without `~`).
* `s3-pbe` (the default set): `plain` codes without `<id>|` and `tilde-noop`.

Runes (13-15 per id): empty, empty with a level, 5 "uniform" pages (one or
two runes per colour), 5 random pages (15% empty slots), one page of event
runes, some levels other than 18, and for the default `preReforged-V7.21`
two `plain` pages (`#<30 ids>`). Reforged (13 per id): empty, 6 full builds,
partial builds (one without primary, one without secondary), 2 named, the
`bare-id` nav link and one `percent-encoded` paste.

## Record format

```json
{"form": "tilde", "hash": "s4-final|~q75M75JPH1xK",
 "expected": {"total": 21, "trees": [{"butcher": 1}, {"enchanted-armor": 1}, {"phasewalker": 1, "inspiration": 2}]},
 "rewrite": "..."}
```

* masteries, classic: `trees` = 3 maps `key -> rank` (tree order offense,
  defense, utility); `name` and `notes` only when set.
* masteries, keystone: `trees` = `{treeId: {key: rank}}` with the keystone
  in its tree map at rank 1, and `keystone` = its key or null.
* runes: `{slots: [30 rune ids or null], level}`; slot order 9 marks,
  9 seals, 9 glyphs, 3 quintessences.
* reforged: `{primary: {path, picks: [keystone, row1, row2, row3]} | null,
  secondary: {path, picks: [row1, row2, row3]} | null, shards: [3 ids or null],
  name}` (ids as the page holds them: numbers for perks, strings for shards).
* `rewrite`: present only when the page writes back something other than
  `hash`. The default sets with nothing in them write an empty hash.

Keys are the slug of the mastery name (lowercase, accents and apostrophes
dropped, other runs of non-alphanumerics become `-`); keystone `id`s already
are such slugs (all 129 keystone entries match their name's slug). Curated
identity aliases (Runic Shield, Veteran Scars, the V3.14 swap, Stoneborn
Pact) belong to `data/patches/masteries-families.json`, not here. Keystone tier lists are in
data order, which is the share-code index order; `slot` is set where the
client drew a mastery elsewhere (`s6-launch` Cunning tiers 2 and 4).

## Baseline screenshots

Not committed: `scratchpad\patches\baseline\shots\` (69 PNGs + `manifest.json`),
taken with `capture-legacy.js shots` from the exported baseline commit over
`file://` at 1440x900 in headless Edge 154. For each of the 23 views (in
`legacy-links.json` `views`): `--empty` (the id with nothing spent),
`--build` (the sample build: the full random build that lights the most
cells) and `--tooltip` (the build plus a real mouse move to the
`tooltip.selector` element: a part-ranked mastery, the first quintessence,
the primary keystone). `manifest.json` records per shot the sha256, any page
errors (none at the baseline) and the tooltip text.

The shooter drives the browser over the DevTools protocol. A capture waits
until the view is drawn (DOM-only conditions, so they also hold for the
reworked pages), web fonts are loaded and the network has been idle for
800 ms; it then finishes every CSS transition / animation (infinite ones are
parked at 0) and takes two screenshots that must agree. Each view is loaded
in 3 independent sessions (`--runs`) and a shot keeps an image that two of
them agree on; `manifest.json` has the count (`agreed`).

`compare` allowance: a pixel counts as changed when a channel differs by
more than 24, and a shot may have up to 16 such pixels. Seen between
sessions: resampling noise on scaled icons (delta up to 10), the
anti-aliased top row of the 7.21 info-bar circle buttons (2-10 pixels at
delta 42), and, in about one session in 30, a few hundred text-edge pixels
(delta 70) or a stale composited strip; the 3-session vote absorbs those.
Two independent full baseline runs compare 69/69 same. For the
after-rework comparison, take a second set with
`shots --worktree --out <dir2>` and run `compare <baseline> <dir2>`; the
tooltip shots need `LolTooltip.isVisible()` / `.element()` from `nav.js`.

## Notes from the capture

* `location.replace("#...")` (the masteries / runes link writers) lands one
  task later in Chrome, so read the hash after a tick; in a `file://` iframe
  Chrome even turns it into a reload of the frame. The tool therefore drives
  top-level pages (copies written next to the real ones, removed afterwards).
* The keystone page does not rewrite the hash when it loads a link; the
  record's `hash` is what `updateKeystoneLink` writes on the next change.
* Baseline defect, not a fixture error: S1 Ardor (`season1-data.js`) has two
  `#` in `desc` and no `rankInfo2`, so its tooltip reads "+#% Attack Speed".
